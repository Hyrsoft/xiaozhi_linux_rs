# 模块设计与使用指南

本文描述当前仓库各模块的职责、数据流、扩展边界和常见使用方式。项目目前是单个 Rust binary crate，`src` 下的接口主要用于仓库内部解耦，并不承诺作为外部 Rust library 的稳定 API。

## 1. 运行时总览

`src/main.rs` 是组合根，负责初始化配置、MCP、GUI、网络、音频与控制器。组件之间通过 `tokio::mpsc` 通道和少量 `Arc` 共享服务连接。

```text
Activation HTTP
      │
      ▼
main ──► NetLink ◄────► Xiaozhi Cloud
 │          │
 │       NetEvent / NetCommand
 │          │
 ├────► CoreController ◄────► GuiBridge ◄────► GUI process
 │          │
 │       AudioEvent
 │          │
 └────► AudioBridge ────────► AudioSystem
                              ├─ capture thread
                              └─ playback thread

Cloud MCP envelope ─► McpServer ─► DynamicTool ─► Process/HTTP/TCP
```

主事件循环监听 Ctrl+C、网络事件、音频事件和 GUI 事件。退出循环后显式调用 `McpServer::shutdown()`，取消仍在运行的外部工具并等待后台任务清理。

## 2. 配置与构建期默认值

### `config.toml` 与 `build.rs`

`config.toml` 保存编译期默认配置。根目录 `build.rs` 解析这些值，并通过 `cargo:rustc-env` 嵌入二进制。它还只在 uClibc target 下编译 `native/auxval_stub.c`；普通应用构建不会下载或编译 ALSA、Opus、SpeexDSP 源码。

适合放在编译期配置中的内容包括默认云端 URL、设备类型、声卡名称、音频参数、GUI UDP 地址，以及首次生成运行时配置所需的默认值。修改 `config.toml` 后需要重新构建。敏感部署值不应长期提交进仓库，生产环境应在部署 `xiaozhi_config.json` 时覆盖。

### `src/config.rs`

`Config::load_or_create()` 在当前工作目录读取 `xiaozhi_config.json`。文件不存在时使用编译期默认值创建；设备 ID 或客户端 ID 缺失时自动生成并保存。

```rust
let mut config = Config::load_or_create()?;
config.validate()?;
config.playback_device = "plughw:1,0".into();
config.save()?;
```

新增配置字段时需要同步更新 `config.toml`、`build.rs`、`Config`、默认值生成逻辑、校验和文档，并明确旧版运行时配置的兼容策略。

## 3. 激活与设备身份

### `src/activation.rs`

`check_device_activation()` 使用 HTTP 接口查询设备状态，返回 `Activated`、`NeedActivation(code)` 或 `Error(message)`。该模块只处理一次查询，重试、GUI 验证码展示和重试间隔由 `main.rs` 管理。

Device ID 优先使用网卡 MAC 地址，无法获取时生成 UUID；Client ID 首次启动生成 UUID 并持久化。两者会用于 WebSocket 和激活请求。

## 4. 网络与云端协议

### `src/net_link.rs`

`NetLink` 独占 WebSocket 连接，负责鉴权请求头、Hello 消息、文本/二进制帧收发、指数退避重连，以及识别 `type=mcp` 信封并交给 `McpServer`。

```text
CoreController --NetCommand--> NetLink --WebSocket--> Cloud
CoreController <--NetEvent---- NetLink <--WebSocket-- Cloud
```

`NetCommand::SendText` 用于协议 JSON，`SendBinary` 用于编码音频。新增云端消息类型通常先扩展 `src/protocol.rs`，再由 `CoreController` 解释业务含义，不建议在 `NetLink` 中加入业务状态判断。

### `src/protocol.rs`

`ServerMessage` 是当前服务端文本消息的宽松反序列化模型。可选字段允许不同消息类型复用同一结构。协议继续扩展时可考虑按 `type` 改为 tagged enum。

## 5. 控制器与状态机

### `src/controller.rs`

`CoreController` 是业务协调器，把网络、音频和 GUI 事件映射成其他组件命令，但不直接读写声卡或 WebSocket。

- server `hello`：发送自动监听命令；
- TTS 状态：更新 `SystemState`、控制上行静音并通知 GUI；
- 云端二进制音频：交给 `AudioBridge` 播放；
- 采集 Opus：通过 `NetCommand::SendBinary` 上传；
- GUI 消息：转发给云端。

### `src/state_machine.rs`

`SystemState` 包含 Idle、Listening、Processing、Speaking 和 NetworkError。状态用于 GUI 展示和决定采集音频是否上传。新增状态时需要同步检查 GUI 状态码映射与服务器事件转换。

## 6. 音频系统

音频模块分为 Backend、Frontend、Codec 和 Bridge 四层，让硬件 I/O、前处理和编码逻辑可以分别替换。

### `src/audio/backend.rs`

`AudioBackend` 负责打开采集/播放流，`CaptureStream` 和 `PlaybackStream` 暴露协商参数、帧读写和错误恢复。

```rust
pub trait AudioBackend {
    fn open_capture(&self, config: &AudioConfig) -> Result<Box<dyn CaptureStream>>;
    fn open_playback(&self, config: &AudioConfig) -> Result<Box<dyn PlaybackStream>>;
}
```

当前生产实现是 `AlsaBackend`，测试实现是 `MockBackend`。自定义 Backend 应保持 S16LE interleaved PCM，`read/write` 返回帧数而不是 i16 样本数，并在 `recover()` 中处理 XRUN 或设备恢复。

```rust
let params = AudioStreamParams {
    sample_rate: 24_000,
    channels: 1,
    period_size: 480,
};
let backend = MockBackend::new(params, params);
backend.push_capture_frame(vec![0; 480]);
```

### `src/audio/alsa_device.rs`

`AlsaBackend` 使用 ALSA 阻塞 PCM，格式固定为 S16LE/RWInterleaved，采样率使用 nearest 协商，缓冲区与 period 根据设备能力协商，并通过 `prepare()` 恢复 XRUN。设备名直接来自 `capture_device` 和 `playback_device`。

### `src/audio/frontend.rs`

`AudioFrontend` 同时定义播放参考帧和采集处理入口：

```rust
fn process_render_reference(&mut self, frame: AudioFrameRef<'_>) -> AfeResult<()>;
fn process_capture(&mut self, frame: AudioFrameMut<'_>) -> AfeResult<()>;
```

- `SpeexFrontend` 保持逐声道降噪和 AGC 行为，当前不消费 render reference；
- `NullFrontend` 原样通过采集帧，适合测试或硬件已完成前处理的设备；
- 后续 AEC Frontend 可缓存播放参考帧，并在 `process_capture` 中完成回声消除。

Frontend 由采集线程独占，不需要内部加锁。实现不得在实时路径中执行网络请求或不可控的长时间阻塞。

### 播放参考帧

播放线程将实际写出的最终 PCM 通过容量 8 的通道提交给采集线程。使用 `try_send`，通道满时丢弃参考帧，不反向阻塞播放实时路径。该通道只提供 AEC 数据路径，目前未实现时钟漂移补偿、延迟估计或 WebRTC APM。

### Codec 与 StreamDecoder

`opus_codec.rs` 负责采集 PCM 的声道转换、重采样、Opus 编码，以及下行 Opus 解码和播放格式转换。`stream_decoder.rs` 为其他下行编码格式保留扩展点。Codec 不直接访问声卡，也不包含 AEC/降噪逻辑。

### `src/audio/audio_system.rs`

`AudioSystem` 创建两个 OS 线程：

- `audio-record`：CaptureStream → AudioFrontend → OpusEncoder → 上行通道；
- `audio-play`：下行包 → StreamDecoder → PlaybackStream，并提交 render reference。

`AudioSystem::start()` 组合 `AlsaBackend + SpeexFrontend`。测试或平台适配使用 `start_with_backend()` 注入 Backend 和 Frontend factory。

### `src/audio_bridge.rs`

`AudioBridge` 把同步音频线程适配为 Tokio 通道：采集包转换成 `AudioEvent::AudioData`，控制器通过 `send_audio()` 提交下行编码包。业务模块只依赖 Bridge，不依赖 ALSA 或 Opus 实现。

## 7. MCP 网关

### 配置与协议

`mcp_gateway/config.rs` 定义 Subprocess/HTTP/TCP transport、sync/background 模式、统一超时和通知扩展点。`protocol.rs` 定义 JSON-RPC 数据结构，`server.rs` 实现 initialize、tools/list 和 tools/call。

### `DynamicTool`

`tool.rs` 负责 MCP arguments 转换、传输选择、结果包装和 sync/background 语义，不直接管理进程组或后台 JoinHandle。

### `ProcessRunner` 与 `ProcessSupervisor`

`process.rs` 提供 `ProcessRequest`、`ProcessResult`、单次执行的 `ProcessRunner` 和后台生命周期管理的 `ProcessSupervisor`。

Unix 子进程进入独立进程组，Windows 使用 Job Object。超时、取消和网关关闭会终止进程树，stdout/stderr 分别最多保留 1 MiB。

新增常规工具只需修改运行时配置；新增传输协议才需要扩展 `ToolTransport` 和 `DynamicTool::execute_inner()`。当前不提供常驻 MCP stdio transport。

## 8. GUI Bridge

`src/gui_bridge.rs` 使用 UDP/JSON 解耦 Core 与 GUI。Core 绑定 local 地址，`send_message()` 向 remote 地址发送数据，接收的 UTF-8 消息通过 `GuiEvent` 交给控制器。

GUI 不是 Core 子进程，Core 不负责启动或监督 GUI。部署时应使用 systemd、容器或板级 init 系统分别管理两个进程。

## 9. Native 依赖与 Cargo sys crate

`crates/xiaozhi-speexdsp-sys` 只暴露当前使用到的最小 SpeexDSP FFI，通过 `links = "speexdsp"` 和 pkg-config 查找库。上层安全封装位于 `src/audio/speex.rs`。Opus 使用 `audiopus_sys` static feature。

新增 C binding 时的优先顺序：

1. 使用维护良好的 crates.io `-sys` crate；
2. 没有合适 crate 时，在 workspace 内建立最小 sys crate；
3. 使用 `links` 防止同一 native 库重复链接；
4. 用 pkg-config 暴露 SDK 的 include/lib 信息；
5. 第三方源码只在 SDK 镜像构建阶段编译。

## 10. Cross SDK 与 CI

### `.cross` 与 Cargo 配置

- `.cross/Dockerfile`：参数化构建工具链、sysroot 和 native 音频库；
- `.cross/docker-bake.hcl`：四目标 Buildx Bake 矩阵；
- `.cross/SOURCE_MIRROR.sha256`：下载资产校验值；
- `Cross.toml`：Rust target 到 GHCR SDK 标签的映射；
- `.cargo/config.toml`：目标 linker 和链接参数。

GNU 目标使用固定 stable，uClibc 使用固定 nightly、rust-src 和 build-std。

### Actions 工作流

`Cross SDK Images` 构建四个 linux/amd64 SDK 镜像，推送 `sdk-v1` 和 commit-SHA 标签到 GHCR。

`Cross Compile` 可选择单一 target 或 all，执行 `cross build --release --locked`、基本 `file/readelf` 检查并上传 binary artifacts。默认 `publish_release=false`，只验证构建；显式开启后才创建 Release。

手动验证顺序：

1. 运行 `Cross SDK Images`，确认四个镜像全部成功；
2. 运行 `Cross Compile`，选择 `all`，保持 `publish_release=false`；
3. 检查四个 matrix job 和 artifacts；
4. 正式发版时才指定版本并开启 `publish_release`。

更详细的镜像版本和 native 链接策略见 [工程基础设施说明](./工程基础设施说明.md)。

## 11. 扩展检查清单

### 新增硬件音频平台

- 实现 `AudioBackend`，不要改 Codec；
- 使用 `NullFrontend` 先验证 I/O；
- 再接入适合硬件的 Frontend；
- 明确 sample rate、channels、period 和 interleaved 约定。

### 新增 MCP 工具

- 优先只增加 `xiaozhi_config.json` 配置；
- 设置合理 timeout；
- 避免 stdout/stderr 超过 1 MiB；
- 长任务使用 background，并设计完成通知方式。

### 升级 native 库

- 更新 Source_Mirror 资产和 SHA-256；
- 发布新的 `sdk-vN`，不要覆盖旧标签；
- ABI 变化时更新 sys crate/FFI；
- 先验证 SDK，再验证四目标应用构建。

### 修改云端协议

- 网络传输留在 `NetLink`；
- 消息模型放在 `protocol.rs`；
- 业务状态转换放在 `CoreController`；
- 避免音频、GUI 或 MCP 模块直接解析云端业务状态。
