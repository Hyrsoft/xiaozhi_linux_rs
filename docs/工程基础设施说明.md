# 工程基础设施说明

运行时各模块的职责、接口与扩展方式见 [模块设计与使用指南](./模块设计与使用指南.md)。

## 交叉编译

仓库使用 cross-rs 和 `Cross.toml` 管理四个 Linux 目标，不再维护按目标复制的 Shell 构建脚本：

| Rust target | SDK image |
|---|---|
| `x86_64-unknown-linux-gnu` | `ghcr.io/haoyn231/xiaozhi-linux-rs-cross:x86_64-gnu-sdk-v1` |
| `aarch64-unknown-linux-gnu` | `ghcr.io/haoyn231/xiaozhi-linux-rs-cross:aarch64-gnu-sdk-v1` |
| `armv7-unknown-linux-gnueabihf` | `ghcr.io/haoyn231/xiaozhi-linux-rs-cross:armv7-gnu-sdk-v1` |
| `armv7-unknown-linux-uclibceabihf` | `ghcr.io/haoyn231/xiaozhi-linux-rs-cross:armv7-uclibc-sdk-v1` |

GNU 目标使用 Rust 1.90.0。uClibc 目标使用 `nightly-2025-09-14`、`rust-src` 和 `build-std=std,panic_abort`。精确的标准库组件列表写在 `.cargo/config.toml`；`Cross.toml` 只负责选择 SDK 镜像，不能再设置布尔值 `build-std = true`。cross-rs 0.2.5 会把该布尔值转换成命令末尾不带组件列表的 `-Zbuild-std`，从而覆盖 Cargo 配置并导致最终 crate 找不到 `panic_abort`。

```bash
cargo install cross --version 0.2.5 --locked

# GNU 示例
cross build --release --locked --target aarch64-unknown-linux-gnu

# uClibc
rustup toolchain install nightly-2025-09-14 --profile minimal --component rust-src
RUSTUP_TOOLCHAIN=nightly-2025-09-14 \
  cross build --release --locked --target armv7-unknown-linux-uclibceabihf
```

## SDK 镜像与 native 依赖

`.cross/Dockerfile` 和 `.cross/docker-bake.hcl` 定义参数化 SDK 矩阵。镜像从本仓库 `Source_Mirror` Release 下载固定版本的工具链、ALSA 1.2.12、Opus 1.5.2 和 SpeexDSP 1.2.1，并使用 `.cross/SOURCE_MIRROR.sha256` 中提交的 SHA-256 强制校验。

ALSA 以共享库形式提供给链接器，运行时使用设备上的 `libasound.so.2`；Opus 与 SpeexDSP 使用 `-fPIC` 构建为静态库。应用构建只通过 pkg-config 和 Cargo sys crate 消费 SDK，不联网、不解压源码，也不运行 autotools/CMake 构建第三方库。

升级 SDK 依赖时应发布 `sdk-v2`、`sdk-v3` 等新标签，不覆盖已发布的 `sdk-v1`。`Cross SDK Images` 工作流同时发布稳定版本标签和带完整 commit SHA 的不可变标签。首次发布前可在具备 Docker Buildx 的 Linux 主机执行：

```bash
docker buildx bake -f .cross/docker-bake.hcl --load x86_64-gnu
docker buildx bake -f .cross/docker-bake.hcl --load aarch64-gnu
docker buildx bake -f .cross/docker-bake.hcl --load armv7-gnu
docker buildx bake -f .cross/docker-bake.hcl --load armv7-uclibc
```

本地验证应检查下载 SHA、`pkg-config` 输出、目标架构、静态库 PIC 属性和工具链版本。应用产物使用 `file` 与 `readelf -d` 检查：ALSA 应出现在 `NEEDED`，Opus/SpeexDSP 不应出现；uClibc 产物应依赖 `libc.so.0` 并包含 `getauxval` stub。Release profile 会移除普通符号表，因此 CI 不用 `readelf -Ws` 查找函数名，而是检查兼容桩中随代码一同保留的 `xiaozhi_auxval_stub_v1` 标记。

## GitHub Actions 构建验证

首次验证或 SDK 内容变化时，先在目标分支运行 `Cross SDK Images`。该工作流需要 `packages: write`，会将四个 `sdk-v1` 镜像和对应 commit-SHA 标签推送到 GHCR：

```bash
gh workflow run cross-images.yml --ref feat/engineering-infrastructure
gh run list --workflow cross-images.yml --branch feat/engineering-infrastructure
gh run watch <run-id>
```

SDK 全部成功后运行应用构建。日常验证保持 `publish_release=false`，只上传 Actions artifacts，不创建 GitHub Release：

```bash
gh workflow run cross-compile.yml \
  --ref feat/engineering-infrastructure \
  -f target=all \
  -f version=build-validation \
  -f publish_release=false
```

工作流验证范围包括：

- `cross build --release --locked` 能否完成；
- 二进制是否为选择的目标架构；
- `libasound` 是否保持动态依赖；
- Opus/SpeexDSP 是否没有出现在动态 `NEEDED`；
- uClibc 产物是否依赖 `libc.so.0`，并包含强制保留的 `getauxval` 兼容桩标记；
- 四个目标是否均生成可下载 artifact。

上述检查只说明构建、链接和产物上传流程正常，不替代真机声卡、网络、MCP 工具或对话功能测试。正式发版时才设置语义化版本，并显式传入 `publish_release=true`。

## MCP 子进程生命周期

`DynamicTool` 只负责 MCP 参数、传输类型和结果转换。`ProcessRunner` 负责单次进程调用，`ProcessSupervisor` 跟踪后台任务并在网关 `shutdown()` 时统一取消和回收。

- stdin/stdout/stderr 均为异步管道。
- Unix 使用独立进程组，Windows 使用 Job Object。
- 超时、取消和关闭会终止进程树。
- stdout/stderr 各限制为 1 MiB，避免外部工具耗尽内存。
- 配置中的 `sync`、`background`、`timeout_ms` 和 `notify` 语义保持兼容。

当前仍是云端 MCP 网关调用一次性外部工具，不提供常驻 MCP stdio transport，也未引入 RMCP。

## 音频边界

音频模块分为三层：

1. `AudioBackend`、`CaptureStream`、`PlaybackStream`：硬件 I/O；当前实现为 `AlsaBackend`，测试实现为 `MockBackend`。
2. `AudioFrontend`：采集前处理和播放参考帧入口；当前实现为保持原有降噪/AGC 行为的 `SpeexFrontend`，以及测试用 `NullFrontend`。
3. Codec：Opus 编解码和重采样保持独立，不属于 Backend 或 Frontend。

播放线程通过容量为 8 的有界通道执行非阻塞 `try_send`，向采集线程提交最终写出的 PCM 参考帧。该接口为后续 AEC 留出数据路径，但当前不包含 WebRTC APM、CPAL、回声消除或唤醒算法。
